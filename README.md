## 2. Образовательный контекст и управление проектом

Quizzle — открытая self-hosted платформа для live-quiz и тренировочных тестов; это следует из [README исходного проекта](https://github.com/gnmyt/Quizzle/blob/c93c5e9e0e137171618c51fb82fe5ca04bd92587/README.md). В данной работе рассматривается сценарий корпоративного обучения: тренер проводит тест после учебного модуля и объединяет результаты с другими отчетами. Это возможный сценарий применения, а не факт внедрения Quizzle в конкретной компании.

Цель доработки: дать тренеру простой табличный файл с каждой сохраненной попыткой, включая повторные прохождения. Исходный Excel-экспорт аналитики сохранен.

GitHub Projects связывает план с Issues и PR, поддерживает таблицу, доску, дополнительные поля и автоматическое обновление данных. В работе использовано табличное представление с полями Title, Status и числовым полем «План, ч». Возможности системы изучены по [официальному описанию Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects) и проверены на созданном проекте.

### 2.1. Что является системой управления проектом

В этой работе система управления — связка **GitHub Issues + GitHub Projects + Git-репозиторий + Pull Requests**, а не сам Quizzle. Quizzle предоставляет учебные тесты, а GitHub организует работу над его изменением. Это не исследование LMS, системы кадрового учета или полноценной корпоративной системы управления портфелем проектов.

Git используется для локальной истории версий и веток. GitHub хранит удаленный репозиторий, запросы и обсуждения изменений. Projects показывает план и состояние задач. Выбор обусловлен тем, что запрос, реализация и доказательства можно связать ссылками в одной среде без отдельного трекера.

Связь объектов именно выполненной работы:

```mermaid
flowchart LR
    need[Потребность тренера] --> issue[Issue 1: критерии]
    issue --> tasks[Issues 2–8: этапы]
    tasks --> project[Projects: статус и план в часах]
    issue --> branch[feature/practice-results-csv]
    branch --> commits[Коммиты кода и проверок]
    commits --> pr[PR 9: Closes 1]
    pr --> merged[Слияние в main форка]
    merged --> done[Закрытая issue и Done]
    commits --> evidence[Файлы и протоколы]
    evidence --> report[Отчет и материалы защиты]
```

### 2.2. Возможности и фактическая настройка

Projects позволяет использовать таблицу, доску или roadmap, дополнительные поля, фильтры и автоматизации. В данном проекте применены **таблица и оценки**, а не все перечисленные возможности. [Официальная документация Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects).

| Объект или настройка | Назначение в работе | Граница использования |
|---|---|---|
| Основная issue #1 | Постановка потребности и приемка функции | Не дублирует трудоемкость семи этапов |
| Issues #2–#8 | Работы T1–T7 с ожидаемыми результатами | Зависимости описаны в плане, календарный график не строился |
| Проект уровня пользователя | «Quizzle: CSV-экспорт результатов», View 1 | Учебный проект одного исполнителя, не проект организации |
| Title, Status, «План, ч» | Наименование, движение работы, числовая оценка | Нет отдельного поля с измеренной фактической трудоемкостью |
| Todo → In Progress → Done | Не начато, выполняется, завершено | Закрытие issue переводит соответствующую карточку в Done |
| Видимость проекта | Итоговый проект открыт для проверки преподавателем | На первоначальном снимке проект еще частный; это историческое состояние |
| PR и комментарий самопроверки | Описание изменения, проверки, связь Closes #1 | Нет независимого APPROVED и заявленного CI-контроля |

Критерий перехода этапа в Done — наличие его контрольного результата, а не только написанного кода. Например, T5 требует выгрузок и протоколов, T7 — готовых отчетных материалов. Поэтому завершение T7 не означает, что уже состоялось выступление.

| Роль в возможном корпоративном процессе | Ответственность | Как представлена в учебной работе |

### 3.2. Архитектура потока результатов

Схема составлена по исходному коду зафиксированной версии, а не по предполагаемой архитектуре:

```mermaid
flowchart TD
    trainer[Авторизованный преподаватель] --> page[React: PracticeResults]
    page -->|POST /api/practice/:code/results| api[Express: requireAuth и маршрут practice]
    api --> files[Файлы data/practice-quizzes/CODE]
    files --> payload[meta, results, studentResults, quiz, analytics]
    payload --> page
    page --> excel[Существующий ExcelExport]
    page --> csv[Новый CsvExport: UTF-8 BOM и экранирование]
    csv --> blob[Blob и временная ссылка]
    blob --> download[Локальный CSV-файл]
```

Сервер читает сохраненные попытки из файловой системы; отдельная SQL-база в этом потоке не используется. Запрос результатов защищен существующим `requireAuth`. CSV формируется на клиенте из уже полученного массива, поэтому новый endpoint и повторная загрузка данных не потребовались.

Основание для схемы: [серверный маршрут](https://github.com/gnmyt/Quizzle/blob/c93c5e9e0e137171618c51fb82fe5ca04bd92587/server/routes/practice.js), [исходная страница результатов](https://github.com/gnmyt/Quizzle/blob/c93c5e9e0e137171618c51fb82fe5ca04bd92587/webui/src/pages/PracticeResults/PracticeResults.jsx), [исходный ExcelExport](https://github.com/gnmyt/Quizzle/blob/c93c5e9e0e137171618c51fb82fe5ca04bd92587/webui/src/common/utils/ExcelExport.js).

## 6. Ветвление и история изменений

Выбран GitHub Flow: отдельная ветка для функции и PR в основную ветку. Для небольшой самостоятельной доработки отдельные `develop` и release-ветки не требуются. Общая последовательность соответствует [описанию GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow).

### 6.1. Почему выбрана эта стратегия

Стратегия ветвления задает, где выполняются изменения и как они попадают в основную версию. Для одной функции с одним исполнителем выбран короткий цикл: создать отдельную ветку от main, сделать связанные коммиты, открыть PR, проверить и слить. Изоляция позволяет сопоставить исходное состояние с конкретной доработкой и сохранить обсуждение рядом с диффом.

В этой работе не требовалось одновременно поддерживать несколько релизов, поэтому дополнительные долгоживущие ветки не вводились. Прямое внесение функционального кода в main также не использовалось: CSV вошел в main через PR #9. После merge выполнен только документационный коммит с итоговыми доказательствами.

Важно различать **fork и branch**: fork LyoshaGodX/Quizzle — отдельный удаленный репозиторий, а feature/practice-results-csv — ветка внутри него. `upstream` обозначает репозиторий автора, `origin` — учебный форк. PR направлен из feature-ветки в main того же форка, не в gnmyt/Quizzle.

Рекомендация GitHub Flow удалять завершенную ветку здесь сознательно не выполнена: она оставлена для учебной проверки. История PR и merge сохранялась бы и после удаления ветки. Внешнее ревью не заменено фиктивным одобрением; это ограничение индивидуальной учебной работы. [GitHub Flow: ветка, PR, проверка и слияние](https://docs.github.com/en/get-started/using-github/github-flow).

## 7. Реализация

Новая утилита [CsvExport.js](https://github.com/LyoshaGodX/Quizzle/blob/34c85084a1f8043d1afe0d1c6dfd5a48decdeec5/webui/src/common/utils/CsvExport.js) разделяет чистое формирование строки и браузерное скачивание. `createPracticeResultsCsv` не меняет входные данные и берет список `results.results` без группировки. `exportPracticeResultsToCsv` создает Blob, безопасное имя файла, временную ссылку и выполняет освобождение ресурсов в `finally`.

В [PracticeResults.jsx](https://github.com/LyoshaGodX/Quizzle/blob/34c85084a1f8043d1afe0d1c6dfd5a48decdeec5/webui/src/pages/PracticeResults/PracticeResults.jsx) добавлены импорт, обработчик и существующий компонент `Button` с иконкой Font Awesome. Сообщения сохранены на немецком языке. В [styles.sass](https://github.com/LyoshaGodX/Quizzle/blob/34c85084a1f8043d1afe0d1c6dfd5a48decdeec5/webui/src/pages/PracticeResults/styles.sass) добавлен `flex-wrap`, чтобы третья кнопка не выходила за границы экрана. Другие экраны, API и файлы данных не изменены.

CSV содержит не аналитические сводки, а строки отдельных попыток. `Timestamp` — время последнего сохраненного ответа из API, не время начала попытки. Порядок строк соответствует данным страницы; отдельное требование сортировки не вводилось.

Контракт утилиты и браузерные ресурсы проверяются в [CsvExport.test.js](https://github.com/LyoshaGodX/Quizzle/blob/34c85084a1f8043d1afe0d1c6dfd5a48decdeec5/webui/tests/CsvExport.test.js). Стандартный тестовый раннер Node.js и уже имеющийся SheetJS позволяют обойтись без новых зависимостей. Изменение не превращает CSV в полную копию Excel-аналитики: в CSV нет сводных листов, группировки и оформления XLSX.

Правила кавычек, запятых и CRLF основаны на [RFC 4180](https://www.rfc-editor.org/info/rfc4180/). BOM добавлен для распознавания UTF-8 в Excel, что описано в [документации Microsoft](https://support.microsoft.com/en-us/office/opening-csv-utf-8-files-correctly-in-excel-8a935af5-3416-4edd-ba7e-3dfd2bc4a032). Префикс для потенциальных формул введен с учетом риска [CSV Injection](https://community.owasp.org/attacks/CSV_Injection).

Интервал от первой записанной отметки до создания PR составил 1 час 4 минуты 6 секунд. Он не включает завершение отчета и материалов защиты и потому не является полным фактическим итогом. В нем есть ожидание входа в GitHub и сетевых операций. Изучение образцов до этой отметки также не включено. Сравнивать этот интервал с общим планом 6 часов как «экономию труда» некорректно: использовалась помощь Codex, отдельного ручного учета по этапам не было.

До контрольной точки готовности отчетных материалов прошло **1 час 26 минут 6 секунд** (86,1 минуты), [машиночитаемая запись](evidence/timing.json). План — 360 минут; разность с этим календарным интервалом — 273,9 минуты, но это не измеренная экономия ручных трудозатрат. После контрольной точки выполнялись окончательная публикация, слияние по разрешению пользователя и сохранение подтверждений результата.

До слияния кода и основного комплекта материалов прошло **1 час 36 минут 19 секунд** (около 96,32 минуты). Разница с планом 6 часов — около 263,68 минуты. Это зафиксированная календарная длительность автоматизированной работы до merge, не ручная трудоемкость; финальные снимки и уточнение этого отчета подготовлены после merge. Часть времени ушла на вход в GitHub, настройку Projects и повторные сетевые запросы. Ускорение реализации с помощью Codex не позволяет переносить такую длительность на обычную самостоятельную разработку.

Функция проверена локально в Chromium на Windows, а не во всех браузерах и версиях офисных программ. UTF-8 BOM не определяет региональный разделитель Excel: при необходимости CSV импортируется с явным выбором UTF-8 и запятой. Защита апострофом изменяет представление формулоподобных имен, что важно учитывать в машинном импорте; она не является универсальной гарантией для всех табличных редакторов и повторного сохранения файла. Экспорт содержит имена, поэтому в реальном корпоративном процессе доступ и передача такого файла должны быть регламентированы организацией.

Задача T7 охватывает подготовку материалов, а не фиктивное подтверждение выступления. Для защиты готовы [сайт](index.html), пятиминутный [сценарий](speech.md), ответы на возможные вопросы и план демонстрации.

## 10. Воспроизведение

### 10.1. Запуск исходного приложения с функцией

Следующие команды выполняются в **репозитории Quizzle**, не в отчетном репозитории. Проверенная среда: Windows, Node.js 24.15.0, Bun 1.4.2. Версии пакетов устанавливаются по существующим lock-файлам.

```powershell
git clone https://github.com/LyoshaGodX/Quizzle.git
cd Quizzle
git switch feature/practice-results-csv
bun install --frozen-lockfile
Push-Location webui
bun install --frozen-lockfile
Pop-Location
node docs/coursework/csv-export/scripts/seed-demo.cjs
```

Скрипт создает только известные демонстрационные каталоги в `data/practice-quizzes` и отказывается заменять уже существующие. На чистой локальной среде создается тестовая учетная запись `coursework` / `CsvPractice2026!`; эти данные предназначены только для демонстрации, не для рабочего сервера. Если пользователи уже существуют, скрипт не изменяет их: нужен вход с имеющейся локальной учетной записью. Файлы `data/` игнорируются Git, токены не публикуются.

Backend и frontend запускаются в двух терминалах:

```powershell
bun server/index.js
```

```powershell
cd webui
bun run dev --host 127.0.0.1 --port 5173
```

Открыть `http://127.0.0.1:5173/`, войти, затем перейти к `/results/NORM`, `/results/EMPT` или `/results/SPEC`. Для проверки CSV нажать `Als CSV herunterladen`.

```powershell
node --test webui/tests/CsvExport.test.js
node docs/coursework/csv-export/scripts/verify-downloads.cjs
node docs/coursework/csv-export/scripts/verify-lint.cjs
Push-Location webui
bun run build
Pop-Location
```

`verify-downloads.cjs` повторно проверяет сохраненные образцы; для новой проверки интерфейса нужно заново скачать файлы. Это команды первоначального комплекта внутри Quizzle; адаптированные копии скриптов в новом отчетном репозитории описаны ниже.

### 10.2. Проверка самостоятельного отчетного репозитория

```powershell
git clone https://github.com/LyoshaGodX/quizzle-csv-export-report.git
cd quizzle-csv-export-report
node scripts/verify-artifacts.cjs
node scripts/verify-downloads.cjs ../Quizzle
node scripts/verify-lint.cjs ../Quizzle
```

Первая проверка требует только Node.js: проверяет локальные ссылки, изображения, якоря и SHA-256 перенесенных оригинальных артефактов. Две другие команды требуют расположенный рядом клон Quizzle с установленными зависимостями webui и проверяют образцы отчета либо исходные файлы функции. Вместо `../Quizzle` можно передать другой путь. Скрипт `seed-demo.cjs` также принимает путь к Quizzle, **но изменяет локальные демонстрационные данные** и не предназначен для рабочего сервера.

Страница [index.html](index.html) статическая: сборка и установка пакетов не требуются. Историческая проверка локальных ссылок сохранена в [artifacts-check.json](evidence/artifacts-check.json), новая проверка комплекта — в [report-check.json](evidence/report-check.json). Первоначальная попытка открыть сайт через `file:` была блокирована встроенным браузером, поэтому визуальная проверка страницы защиты не заявлялась. Это не относится к уже проверенному интерфейсу Quizzle на HTTP. Публичная публикация страницы и ее фактический статус фиксируются отдельно в [PUBLICATION.md](PUBLICATION.md).

### 10.3. Происхождение и сохранность приложений

В [ARTIFACTS.md](ARTIFACTS.md) перечислены все исходные файлы и назначение групп. Снимки, CSV, XLSX, фикстуры, планы и первоначальные протоколы перенесены без изменения байтов. Оригиналы переработанных README, сайта, сценария и скриптов сохранены в `source-artifacts/`. Их относительные ссылки относятся к первоначальному месту в Quizzle; для навигации следует использовать этот отчет.

Манифест [source-manifest.json](evidence/source-manifest.json) связывает каждый исходный файл с путем в новом репозитории и SHA-256. Он подтверждает сохранность переноса, но сам по себе не заменяет историю Git, не доказывает дату снимка и не является электронной подписью.

## 11. Выводы

В Quizzle добавлен CSV-экспорт отдельных попыток тренировочного теста. Функция соответствует заранее описанным критериям, сохраняет существующий Excel-экспорт и не требует изменения серверного API. Основные сценарии подтверждены автоматическими проверками и скачанными через интерфейс файлами.

GitHub Issues, Projects, feature-ветка и PR позволили сохранить связь между запросом, оценкой времени, изменением кода и доказательствами результата. Первоначальный план и снимки до реализации находятся в истории Git. Отчет и материалы защиты подготовлены; публичное выступление и приемка в реальной организации не заявляются как выполненные.

По отношению к заданию завершен цикл постановки, планирования и реализации функции в существующем веб-проекте. Новый репозиторий отделяет итоговый отчет от кода и позволяет проверить результат без запуска Quizzle. Для закрытия части «Публичное выступление» студенту остается провести защиту и при наличии согласия участников добавить фактический протокол или разрешенные фотографии. Заготовка протокола не считается доказательством выступления.
